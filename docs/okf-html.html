OKF-HTML v0.1 Profile

This profile defines how Open Knowledge Format (OKF v0.2) documents are stored as self-contained HTML instead of Markdown. Storage format is selected per document — HTML (default) or Markdown; each document exists in exactly one format, with no mirrors and no sync. Markdown documents remain governed by the existing OKF v0.2 markdown spec (YAML frontmatter); this profile covers the HTML side. The okf-god catalog indexes both formats as first-class entries.

This document is the format contract. It is authored in OKF-HTML itself and doubles as the reference fixture for the okf-god parser tests.

Document skeleton

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Architecture</title>                     <!-- maps to `title` -->
  <meta name="okf:type" content="doc">            <!-- §4.1 fields -->
  <meta name="okf:resource" content="okf-html">
  <meta name="okf:status" content="stable">
  <meta name="okf:stale_after" content="2027-01-01">
  <meta name="okf:generated.at" content="2026-11-24T10:00:00Z"> <!-- dotted keys -->
  <meta name="okf:tags" content="format">         <!-- lists: repeat the tag -->
  <meta name="okf:tags" content="okf-god">
</head>
<body>
  <!-- semantic HTML body -->
</body>
</html>

Rules

  1. Scalars: one <meta name="okf:<field>" content="<value>"> per field. Dotted YAML keys map 1:1 to dotted meta names (generated.at → okf:generated.at).
  2. Lists (tags, sources): repeat the same meta name; order = document order.
  3. Title: the <title> element maps to the title field; no okf:title meta is needed. name="description" (plain HTML) is accepted as a fallback alias for the description field; okf:description wins when both exist.
  4. Permissive (§11): unknown okf:* fields are tolerated; zero okf: metas is a valid permissive document (entry indexes with name only). The parser never throws and never rejects a document.
  5. Reserved filenames: index.html and log.html are not cataloged (mirrors §3.1 index.md/log.md).
  6. Links (§6): <a href="pi.html"> and extension-less bundle-relative /pi are concept links. Extension-less targets are format-agnostic: resolved against the entry's root, then same-kind roots, trying .html first (default), then .md. Exact relative paths (../PLAN.md) resolve against the source file's directory. http(s):, mailto:, #anchor are ignored. Broken links are tolerated and kept, never rejected.
  7. Mixed bundles: .md and .html coexist in one catalog; format is selected per document, defaulting to HTML for new docs.
  8. Names: doc slug = filename minus extension (pi.html → pi); skill and agent naming rules are unchanged (they stay Markdown).
  9. Slug collisions: pi.md and pi.html in the same root both index (distinct paths). Name-based lookup prefers the .html entry (default format); exact-path lookup is unambiguous.

Link authoring guidance

In HTML documents, prefer extension-bearing relative hrefs (pi.html, ../docs/pi.html): they stay clickable when the file is opened in a browser under file://, and the okf-god graph resolves them. The extension-less /name form is supported for graph parity with Markdown's /x.md convention, but renders unclickable in browsers, so treat it as a fallback, not the house style.
